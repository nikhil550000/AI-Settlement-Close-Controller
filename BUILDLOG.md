## Session 1.3 — 2026-08-27 — Generator core, clean-case path, `generate` CLI

**Built**

- `generator/rounding.py`: `percentage_of_paise(base: Paise, percent: Decimal) -> Paise` — the one place `decimal.Decimal` with `ROUND_HALF_UP` is permitted (§4.5), cast to `Paise` immediately. Used for both the 2% MDR fee and the 18% GST-on-fee derivation.
- `generator/clean.py`: `generate_clean_batch(rng, snapshot_date, n_settlements=18) -> CleanBatch`. Generates the §3.5 "Fully clean" population (n=18 by default, matching the case-allocation table) — settlements, their payment `recon_line`s, and the correct accrual-basis ledger posting for each payment: `Dr Razorpay Clearing (net), Dr Payment Gateway Charges (fee), Dr GST on Gateway Charges (tax) / Cr Sales Revenue (gross)`, the same entry worked out in §3.2's family-3 example. Payment amount uses a lognormal in the stated `₹100-₹50,000` range, median `~₹1,500`, with `sigma` chosen as generator config since the spec states the shape and range but not `sigma` (see Decided).
- A single `random.Random(seed)` instance is created once (in `generator/cli.py`) and threaded through every generation call — no second RNG instance, no unseeded `random.*` call anywhere under `generator/`. Writes `settlements.jsonl`, `recon_lines.jsonl`, `ledger_entries.jsonl` to `scratch/generated/` (gitignored — this is a dev run, not yet the committed reference batch, which doesn't exist until Phase 2's anomaly populations complete it).

**Cut**

- Refund generation, adjustment generation, and bank-statement-line generation are explicitly **not** in this session, even though §3.5's "record shape" section states refund/adjustment volumes as part of the batch's overall composition. Reason: a "correctly booked, non-anomalous refund" has no defined journal entry anywhere in spec.md — only family 2's *anomalous* (missing) refund posting is specified (§3.2) — so building one now would invent an accounting treatment ahead of the spec rather than transcribe one. Refunds and adjustments arrive with the family injections in session 2.1. `bank_line` generation is Phase 2/3 territory (§4.6's UTR-variety obligation, the three-profile adapters) and isn't needed by any of the three Phase 1 checkpoint assertions.

**Decided**

- `sigma = 0.8` for the payment-amount lognormal (mu = ln(1500)), clipped to `[₹100, ₹50,000]`. Spec states the distribution family, range, and target median explicitly but leaves the spread unstated; §3.5 itself frames these draws as "generator config," so this is logged as a config choice rather than treated as an ambiguity requiring a stop-and-ask.
- Ledger entries are booked with `source = erp_import`, not `manual` — these represent the merchant's own bulk-imported bookkeeping, which is the closer fit of the two non-`controller_adjustment` enum values (§3.1) since nothing here is a hand-keyed single entry.
- Each ledger leg gets its own `journal_entry_id`; multiple legs of the same economic transaction share a `reference` (the `recon_line.entity_id`) instead. Read `journal_entry_id string, unique` (§3.1) literally as a per-row key rather than a per-transaction voucher number — the schema has no separate "voucher ID" field, and `reference`'s stated purpose ("external ref: payment ID, invoice ID") is exactly the transaction-grouping key a flat ledger export needs.
- IDs (`pay_*`, `setl_*`, `je_*`, UTRs) are drawn from the RNG as random hex/base36, not sequential counters — §3.5's "Fingerprint control" (global shuffle, shared narration pool) is explicitly session 2.3's job, but there's no reason to hand that session a sequential-ID population to un-fingerprint when random IDs cost nothing now.
- Output goes to `scratch/generated/` (already gitignored as "run scratch output" per Session 1.1), not `data/`. `data/` is reserved for the committed seeded reference dataset (§6.4), which only exists once Phase 2's anomaly populations make the batch real; this session's output is a dev run proving the generator core works, not that artifact.

## Session 1.2 — 2026-08-27 — Four §3.1 schemas, `Paise` alias, SQLite DDL

**Built**

- `pipeline/money.py`: `Paise = NewType('Paise', int)` per §4.5, plus `NonNegPaise = Annotated[Paise, Field(ge=0)]` used on every money field across the four schemas — every amount in §3.1 is a magnitude (a debit leg, a credit leg, a fee, a settlement total), never a signed net figure, so non-negativity is boundary validation, not an invented constraint.
- `pipeline/schemas.py`: the four §3.1 canonical schemas as frozen (immutable) Pydantic v2 `BaseModel`s — `ReconLine`, `Settlement`, `BankLine`, `LedgerEntry` — plus their four enums (`RazorpayEntityType`, `SettlementStatus`, `BankProfile`, `LedgerSource`) as `enum.StrEnum`. - `LedgerEntry` carries a `model_validator` enforcing the §3.1 rule stated in prose — `resolution_id` and `case_id` are set if and only if `source == controller_adjustment` — since this is a real cross-field rule the spec states explicitly, not an invented one.
- `pipeline/storage.py`: raw `sqlite3` DDL for the `ledger_entry` table with `UNIQUE(case_id, resolution_id)`, plus a minimal `connect()` / `insert_ledger_entry()` pair — enough to make the constraint testable, nothing beyond that (no idempotency pre-check logic, no query helpers; that is Phase 4's `apply.py`).
- `tests/test_schemas.py`: one round-trip test per schema (construct → `model_dump_json` → `model_validate_json` → equality), plus two tests for the `LedgerEntry` cross-field validator (rejects `resolution_id`/`case_id` set without `controller_adjustment`, and rejects `controller_adjustment` without them).
- `tests/test_storage.py`: insert-and-read-back, a duplicate `(case_id, resolution_id)` insert raising `sqlite3.IntegrityError`, and a check that two `manual`/`erp_import` entries (both `case_id = NULL, resolution_id = NULL`) do *not* collide — documenting that SQLite treats NULLs as distinct under `UNIQUE`, which is the behavior the idempotency invariant actually needs.
- Full suite green: 11 passed (import guard + 7 schema tests + 3 storage tests). Verified no `float`, `datetime.now()`, or unseeded `random` anywhere under `pipeline/`.

**Broke**

- Nothing broke. Schemas and DDL are new, additive code with no prior behavior to regress.

**Cut**

- Nothing cut. Session scope was the four schemas, `Paise`, and the DDL only — no adapter, generator, or validator-chain code, per the session-decomposition table.

**Decided**

- Schemas live under `pipeline/`, not a new top-level `schemas/` package. §4.1 says the generator is a separate entry point the pipeline never imports, but does not forbid the reverse; since these are described as "canonical *input* schemas" to the pipeline, and data flows generator → pipeline, having the generator import `pipeline.schemas` in a later session is the correct direction and keeps the import guard's one-way rule intact (confirmed: the guard only scans `pipeline/`, so this is unaffected either way).
- All four schemas are `frozen=True`. Only `recon_line` is explicitly called "never mutated" in the spec text, but none of the other three are working state either — they are raw external evidence, an adapted bank line, or a posted journal fact — so immutability was extended to all four for consistency rather than left as an inconsistent special case.
- Did **not** restrict `LedgerEntry.account_code` to an enum of the 7 §3.2 chart-of-accounts codes, even though the COA is locked and small. §3.1's schema block states `account_code` as a plain string with an FK comment; enforcing "account permitted for this template" is explicitly Phase 4 validator-chain territory (invariant 1.7.5, session 4.3). Encoding it here would pre-empt that check with a cruder one and risk conflicting with how the validator chain is actually specified to work.
- Did **not** enforce the `entity_id` prefix convention (`pay_*`, `rfnd_*`, `trf_*`, `adj_*`) as a regex/pattern constraint — that comment in §3.1 reads as illustrative, not a stated requirement, and inventing it risks rejecting a legitimately-shaped real payload.

## Session 2.3 — 2026-08-27 — Global shuffled ID pass, shared narration pool, §4.6 UTR variety, fingerprint assertions

**Built**

- `pipeline/fingerprint.py` — the one statistic every fingerprint check rests on. Order the batch by some *artifact* (position in the emitted file, lexicographic identifier, `created_at`, narration text), label each record with the population that produced it, and count same-population neighbours; `scenario_block_statistic` compares that count against its **exact** mean and variance under a uniformly random permutation of the same label multiset and reports a z-score. The null moments are closed-form (falling factorials over the label counts), so the check is deterministic and needs no second RNG. Lives under `pipeline/` for the same reason the schemas and ground truth do: §5.3 requires the metrics JSON to carry this as a reported pass/fail line, the eval harness that writes it is pipeline-side, and `pipeline/` may never import `generator/` (§4.1). It takes plain label sequences, so it imports nothing from either package.
- `tests/test_fingerprint_statistic.py` — the moment formulas checked against a seeded Monte-Carlo of the same null across four label multisets, plus the threshold's teeth (a scenario-sorted sequence must be flagged) and its one soft spot pinned (with two labels a random permutation is already near-saturated, so blocking scores only ~9σ; with the batch's ~19 small populations it scores far higher).
- `generator/narration.py` — every free-text string the generator writes, in one module, with no function taking a scenario, family, template id, or subtype as an argument. Ledger narrations, settlement-credit narrations, reversal/debit/charge narrations, counterparty and payer names, adjustment descriptions, UTR minting, and the four §4.6 `UtrShape` text shapes. `narration_template()` reads a narration back to the pool template that wrote it — the checkpoint needs the shape recovered from the text to ask whether *sentence choice* correlates with scenario — and it raises rather than returning `None`, so a string written from outside the pool fails loudly.
- `generator/finalize.py` — the global pass, run once over the assembled batch, in three steps. (1) **IDs**: every identifier in the batch re-minted in one globally shuffled order, namespace preserved (`pay_`, `setl_`, `je_`, `bank_`, `orphan_`, ...), with every cross-reference moved with it — including the ones inside §1.6's `expected_resolution` prose, rewritten by regex over the id shape. **Broke**

**Decided**

- **The ID pass was implemented literally, the timestamp pass was not**, and the asymmetry is deliberate. Re-minting identifiers buys nothing measurable on its own — the generator already drew them from a uniform 32-bit source, so no ordering statistic can tell the before from the after — but it makes the property *structural* rather than incidental: a future session that introduces a sequential id is neutralised by a pass that already exists, and the collision risk on ~5,800 independent draws is closed as a side effect. Timestamps could not be given the same treatment without destroying the evidence, so they were fixed at the source instead. The rule applied throughout: where the spec names a means, implement the means if it can be implemented without destroying what it protects; where it cannot, implement the end and assert it.
- **UTR length raised from 9 characters to 16**, the length of a real NEFT/RTGS UTR, minted as four uppercase letters and twelve digits. §4.6 tier 1 accepts "a contiguous prefix of length ≥ 8"; at 9 characters there was exactly one legal truncation length, making the truncated population a single degenerate case rather than a range. The generator holds itself to a 10-character minimum prefix rather than the spec's 8 — at 8 characters a written-prefix collision across ~100 settlements is remote but real, and a collision would put two settlements in the same tier-1 candidate set and silently corrupt a match the eval then grades. Which tier `EMBEDDED` lands at depends on how session 3.3's matcher tokenizes, which is that session's call; §4.6's generator obligation is the variety, not the tier. That produced `401 The API key you provided is invalid` on a *raw* `requests`-shaped call, while the *same* key through the `openai` SDK had already been producing `404`s — two different error codes from what looked like one cause, which is what made the account-level 404s worth doubting for a moment. Root-caused by dumping the parsed value's length/prefix/suffix (never the full key) and finding the leading/trailing `"`. Fixed by stripping a matched leading/trailing quote pair in the env loader; not a change to any committed module — `pipeline/llm_client.py` reads `os.environ` directly and was never the source of the bug, only ever a debugging script's parsing was.
- Nothing in `pipeline/` regressed. `pipeline/predicates.py`, `pipeline/instantiator.py`, `pipeline/validator.py`, `pipeline/policy.py`, `pipeline/reconciliation.py`, and every generator module were untouched; the full 361-test pre-existing suite (337 through session 4.3, plus session 5.1's 24) stayed green throughout.

**Decided**

- **Populating and committing a real cache now, ahead of the formal FR-13 pin, is in scope for this session and not a jump ahead of session 7.2's job.** The cache is content-addressed by prompt hash, not by seed or run identity, so a cache built now is forward-compatible with whatever batch is later formally pinned — nothing about it needs to be redone, only extended if the pinned batch's prompts differ. Session 7.2 still owns tying seed + git SHA + model ID + metrics JSON together as one pinned, reproducible unit; this session only needed the cache mechanism proven against something real, per §6.3's own checkpoint wording ("the cache is committed").
- **The automated test suite stays 100% network-free, and the real-account verification lives outside `pytest` entirely**, as a scratch driver script rather than a committed test. A checkpoint test that requires a live Fireworks key would make NFR-05's "fully offline mode" claim false the moment CI or a judge's machine has no key — exactly the failure mode `CacheMode.STRICT` exists to rule out. The real verification was still done, and done twice (population, then two independent strict passes with no key present), just not wired into the thing that has to run everywhere.
- **The model swap is logged where the constant lives (`FIREWORKS_MODEL_ID`'s own docstring) and in this entry, not as a formal spec.md revision.** §4.4's own "Assumption" callout already grants exactly this: "the exact model ID MUST be re-checked against the live catalog before it is pinned... the pinned ID is recorded in the metrics JSON alongside seed and SHA." Swapping model *family* (Llama → an OpenAI open-weight MoE) rather than only version is a larger deviation than that sentence's literal framing anticipates, which is why it's called out explicitly here and in code rather than treated as a routine one-line config change — but the sentence's permission, and the requirement to record the ID once pinned, both already cover this case; no locked section states or assumes `llama-v3p3-70b-instruct` specifically anywhere outside §4.4 itself.
- **`classified_subtype` is recorded on every `CaseOutcome` a classification reaches, not only the branch it can change.** Considered restricting it to the "no candidates" branch (the only one `classified_unmatched_inbound_credit` affects) and rejected: the FR-06/date-error `REVIEW_REQUIRED` cases still get classified (as `AMBIGUOUS_CASE`, per session 5.1's documented "least-wrong answer" fallthrough) and a future report reading "what did component 5 say about this case" should not have to re-derive it from a different code path than every other case uses.
- **`build_slot_a_prompt` excludes `case_id` deliberately**, not as an oversight caught in review. Two cases with byte-identical evidence (same case kind, same fired triggers, same narration) are, from Slot A's point of view, the same question, and charging twice for one answer — in both API cost and cache-file size — would be paying for information (an internal bookkeeping ID) invariant 1.7.2's boundary already excludes from what the model is given.
